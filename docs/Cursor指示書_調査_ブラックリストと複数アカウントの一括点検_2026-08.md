## 0. 背景とゴール

オーナーからの相談：

> 最近怪しい会員が入ってきたかもしれない。過去にブラックになった人間かどうか確認したい。
> ブラックリストだけでなく、複数アカウントも同時に調べたい。

### こちらで先に調べて分かっていること

- 会員登録時に **`checkBlacklist`** という Cloud Function が呼ばれ、
  **`blacklist` コレクション**の `fullName` / `email` と **完全一致**したら登録を拒否する仕組みがある
- しかし **`blacklist` コレクションに書き込む処理がコード上に1つも存在しない**
  （`functions/src/index.ts` の 372行目で読み取っているだけ）
- つまり、管理画面でイエローカード3枚やレッドカードを出して `status` を `blacklisted` にしても、
  **`blacklist` コレクションには何も追加されない**
- 手作業で直接登録していない限り、**この防止機能は一度も働いていない可能性が高い**

### このタスクで確かめたいこと

1. `blacklist` コレクションは実際に何件あるのか（＝防止機能は機能していたのか）
2. 締め出したはずの人が、**別アカウントで戻ってきていないか**
3. **複数アカウント**の最新状況（前回調査から会員が増えている）
4. とくに **直近60日に登録した会員**の中に、疑わしいものがないか

## 3. 実行方法

- 新規スクリプト: `scripts/check-suspicious-accounts.mjs`（リポジトリに置いてよい。**出力ファイルは置かない**）
- 認証は既存の `scripts/check-duplicate-accounts.mjs` と同じ方式（Firebase CLI トークンで Firestore REST 読み取り）
- **新しい依存パッケージを `package.json` に追加しないこと**
- 実行時に **総読み取り件数を表示**すること

### 正規化ロジックは既存と必ず同一にすること

氏名・メールアドレスの正規化は、`scripts/check-duplicate-accounts.mjs` と **完全に同じ実装**を使うこと。

- **推奨**: `scripts/lib/normalize.mjs` に切り出し、既存スクリプトと新スクリプトの両方から読み込む
- 切り出しが難しければコピーでもよいが、**その場合は第7章のテストケースで同一性を必ず確認すること**
- **2つのスクリプトで判定結果が食い違う状態を作らないこと**

#### 正規化の仕様（再掲・厳守）

**メールアドレス**

1. 前後の空白除去 → 小文字化
2. `@` でローカル部とドメイン部に分割
3. `googlemail.com` → `gmail.com`
4. `+` 以降の除去 … `gmail.com` / `icloud.com` / `me.com` / `mac.com` / `outlook.com` / `outlook.jp` / `hotmail.com` / `hotmail.co.jp` / `live.jp` / `live.com` **のみ**
5. ドットの除去 … **`gmail.com` のみ**

> ⚠️ `docomo.ne.jp` `ezweb.ne.jp` `au.com` `softbank.ne.jp` `i.softbank.jp` `icloud.com` は
> **ドットの有無で別人**です。ここでドットを消すと無関係な人を誤検知します。

**氏名**

1. 前後の空白除去
2. 全角・半角スペースを**すべて除去**
3. 全角英数 → 半角
4. ひらがな → カタカナ
5. アルファベットは小文字化

## 4. 調べること

### 4-1. `blacklist` コレクションの実態

- **件数**
- 各ドキュメントが持つ**項目名の一覧**（`fullName` `email` 以外に何があるか）
- 作成日らしき項目があれば、その分布
- `fullName` / `email` が**空のドキュメントが混ざっていないか**
  （空文字が入っていると、完全一致で誤ヒットする恐れがある）

**0件だった場合も、そのまま「0件」と報告すること。** それ自体が重要な結論です。

### 4-2. 現在ブラックリスト状態の会員

`users` のうち `status === 'blacklisted'` のもの。

- 件数
- 各件の 会員番号 / 氏名 / メール / 生年月 / `yellowCards` / 登録日 / 累計お得額

### 4-3. 突き合わせ（防止機能が働くか）

4-2 の各会員について、**4-1 の `blacklist` に登録されているか**を判定する。

| 判定 | 意味 |
|---|---|
| 登録済み（完全一致） | 同じ氏名・メールで再登録しようとすれば弾ける |
| 未登録 | **同じ氏名・メールでも素通りで再登録できる状態** |

**「未登録」の件数を必ず報告すること。** これが今回いちばん重要な数字です。

### 4-4. 出戻りの検出（過去ブラック → 別アカウントで復活）

4-2 の会員（および 4-1 の `blacklist` 掲載者）を「照合元」とし、
**現在 `status === 'active'` の会員全員**と突き合わせる。

| 確度 | 条件 |
|---|---|
| **高** | 正規化後のメールアドレスが一致 |
| **高** | 正規化後の氏名が一致 **かつ** `birthMonth` も一致 |
| **中** | 正規化後の氏名が一致（生年月は不一致） |
| **低** | メールのローカル部（`@`の前）が一致し、ドメインだけ違う |

- 同一 uid どうしの自己一致は除外する
- `role === 'admin'` は全判定から除外する
- 1組が複数条件に当たる場合は、**最も高い確度で1回だけ**出す

### 4-5. 複数アカウントの再検出

`status` を問わず（admin は除く）**全会員**を対象に、前回と同じ基準で重複を検出する。

| 確度 | 条件 |
|---|---|
| 高 | 正規化後のメールが一致 |
| 高 | 正規化後の氏名が一致 かつ `birthMonth` 一致 |
| 中 | 正規化後の氏名が一致（生年月は不一致） |
| 低 | ローカル部一致・ドメイン違い |

**前回（2026-08時点）は 21グループ / 45アカウント**でした。**前回との差分**（新たに増えたグループ）が分かるように報告してください。

あわせて、各グループについて次を出すこと（前回オーナーが判断材料にした項目）。

- 登録日の**間隔（日数）**
- **同じ日に登録されているか**、会員番号が**連番か**
- **累計お得額が2件以上でプラスか**（＝両方のアカウントが実際に使われている）

### 4-6. 直近60日の新規登録者に絞った一覧

`createdAt` が **直近60日以内**の会員を抽出し、そのうち 4-4 または 4-5 で疑いがかかったものだけを別ファイルに出す。

- 日数は **コマンドライン引数か環境変数で変更できるように**すること（既定値60）
- 「最近入ってきた怪しい会員」への回答にあたる部分なので、**ここは特に見やすくまとめること**

## 6. ⚠️ この調査の限界（サマリーに必ず明記すること）

**「過去にブラックだった」という履歴は、システム上どこにも残っていません。**

- 分かるのは **現在** `status === 'blacklisted'` の人だけ
- イエローカードを取り消して `active` に戻した人は、**ブラックだった事実が消えている**
- `blacklist` コレクションだけが唯一の履歴になり得るが、自動追加の仕組みが無い

したがって、**この調査で「出戻りなし」となっても、それは「見つからなかった」であって「いない」ではありません。**
サマリーにこの旨をはっきり書いてください。

## 0. 進め方（重要）

このタスクは **サブエージェント3体＋とりまとめ** で進めてください。

| 役 | やること | 独立性の条件 |
|---|---|---|
| **A：実装役** | 第2章の仕様どおりに実装する | — |
| **B：検証役** | **実装役の報告を読まずに**、第2章の仕様書だけを見てコードを検証する | **A の作業ログ・報告文を渡さないこと** |
| **C：横断調査役** | 「同じ付け忘れ」が他にないかコードベース全体を調べる | A・B と独立に走らせてよい |
| **とりまとめ** | A・B・C の結果を突き合わせ、食い違いも含めて1本の報告にする | — |

### B（検証役）を独立させる理由

今回の不具合は「アイコンを描く場所が4つあるのに1つしか色分けが入っていなかった」という**付け忘れ**で起きています。
実装した本人が検証すると「指示どおり書けたか」を見てしまい、「**仕様上あるべき場所を全部拾えたか**」が抜けます。

そのため B には、**A が何をどう直したかを一切渡さず**、第2章の仕様だけを起点に
「仕様上こうなっているはずの箇所」を自分で探させて突き合わせてください。
A の報告を追認させると、この構成の意味がなくなります。

### この構成の限界（必ず理解しておくこと）

**サブエージェントはブラウザを操作して「実際に色が変わるか」を確認できません。**
コード上の整合性は確認できますが、動作確認にはなりません。
最終的な目視確認はオーナーが行います（第6章）。
**報告に「検証済み」と書くときは、必ず「コード上の検証であり、実機の目視確認は未実施」と明記してください。**

### このタスクの終了地点

**ローカルでのコミットまで。push とデプロイはしないでください。**
オーナーが目視確認を終えてから、あらためて push / デプロイの指示を出します。

## 2. 実装仕様（A：実装役への指示）

### 2-1. 色を決める共通関数を新規作成

**新規ファイル**: `src/lib/userAvatar.ts`

```ts
/**
 * イエローカードの枚数からアバターの背景色を決める。
 * 0枚 → 通常の青 ／ 1枚 → 黄 ／ 2枚以上 → 橙（警戒）
 *
 * ※ 3枚到達＝ブラックリスト（status: 'blacklisted'）は 2枚以上に含まれるため橙になる。
 *   停止中であることは色ではなく「停止中」バッジで示す（getAvatarBg では扱わない）。
 */
export function getAvatarBg(yellowCards: number | null | undefined): string {
  const yc = typeof yellowCards === 'number' && Number.isFinite(yellowCards) ? Math.max(0, yellowCards) : 0
  if (yc >= 2) return '#f97316'
  if (yc === 1) return '#eab308'
  return '#0095B6'
}
```

- 色の値は **現行の顧客リストと同じもの**を使うこと（`#f97316` / `#eab308` / `#0095B6`）。**新しい色を発明しない。**
- ブラックリスト専用の色（赤など）は **作らない**。オーナー指定は「橙＋停止中の表示」。

### 2-2. アバターの共通コンポーネントを新規作成

**新規ファイル**: `src/components/UserAvatar.tsx`

- 役割は **「丸・頭文字・背景色」だけ**。
- **未読ドットやイエローカード枚数バッジは、このコンポーネントに含めない。** 呼び出し側の既存実装のまま残すこと（変更範囲を最小にし、崩れるリスクを減らすため）。

```tsx
import { getAvatarBg } from '../lib/userAvatar'

interface Props {
  /** 表示名（先頭1文字をアイコンに出す） */
  fullName: string
  /** イエローカード枚数。未取得なら 0 扱い */
  yellowCards: number | null | undefined
  /** 円の直径（Tailwind のサイズ指定にそのまま使う） */
  size?: 'xs' | 'sm' | 'md'
  className?: string
}

const SIZE = {
  xs: { box: 'w-7 h-7', text: 'text-[10px]' },
  sm: { box: 'w-9 h-9', text: 'text-sm' },
  md: { box: 'w-10 h-10', text: 'text-sm' },
} as const

export default function UserAvatar({ fullName, yellowCards, size = 'md', className = '' }: Props) {
  const s = SIZE[size]
  return (
    <div
      className={`${s.box} rounded-full flex items-center justify-center flex-shrink-0 transition-colors ${className}`}
      style={{ backgroundColor: getAvatarBg(yellowCards) }}
    >
      <span className={`text-white font-bold ${s.text}`}>{fullName.charAt(0)}</span>
    </div>
  )
}
```

- サイズは **現行の各箇所と同じ大きさ**になるよう割り当てること（下表）。**見た目の大きさを変えない。**

### 2-4. ブラックリストの会員を顧客リストに残す

**変更する箇所（1箇所だけ）**: `src/pages/AdminDashboard.tsx` 164行目付近

```ts
// 変更前
const q = query(collection(db, 'users'), where('status', '==', 'active'))
// 変更後（status で絞らず全件取得する）
const q = query(collection(db, 'users'))
```

**⚠️ 絶対に触ってはいけない他の `status === 'active'` 絞り込み**

以下は **別の目的**で active に絞っており、ここを一緒に変えると**停止中の会員にクーポンが配られる**などの事故になります。**触らないこと。**

- `src/components/CouponManager.tsx` 152行目付近（クーポン配信対象）
- `src/components/AnalyticsManager.tsx` 153行目付近（分析の母数）
- `src/components/UserManager.tsx` の各所（会員番号の採番対象、一斉配信対象、操作ボタンの活性制御など）

**顧客リストに「停止中」の表示を追加する**

顧客リストの各行（`sortedUsers.map` 内）で、`user.status === 'blacklisted'` のとき小さなバッジを出す。

- 文言は **「停止中」**
- 既存のバッジ類（`totalSavedAmount` の表示など）と同じ行に並べ、**レイアウトを崩さない**
- 目立ちすぎない配色にする（例：グレー系の背景に濃いグレーの文字）。**アイコンの橙と競合させない**

**自動選択の候補から停止中を除く**

431行目付近の「先頭を自動選択する」処理は、現在 `role !== 'admin'` で絞っている。
ここに **`u.status !== 'blacklisted'`** を加え、画面を開いた瞬間に停止中の会員が自動選択されないようにすること。
（ただし、オーナーが自分でタップして選んだ場合は今までどおり開けること。）

**「会員情報を一覧から読み込めません」の画面は残すこと**

1601行目付近のフォールバック画面は、削除アカウントなど他の要因でも起こりうるため **そのまま残す**。

### 2-5. 付与直後の即時反映

`AdminDashboard.tsx` の `handleYellowCard` と `handleRedCard` で、`updateDoc` 成功後に
**ローカルの `users` も即座に書き換える**（楽観的更新）。`setUsersRefreshKey` は現行どおり残す。

```ts
await updateDoc(doc(db, 'users', selectedUser.uid), update)
// 再取得を待たずに画面へ反映する
setUsers((prev) =>
  prev.map((u) =>
    u.uid === selectedUser.uid
      ? { ...u, yellowCards: next, status: (update.status as string) ?? u.status }
      : u,
  ),
)
setUsersRefreshKey((k) => k + 1)
```

- `update` に `status` が入っていないときは **元の status を維持**すること（上書きで消さない）。
- `handleRedCard` も同様に、`yellowCards: 3` と `status: 'blacklisted'` を反映すること。
- `UserManager.tsx` 側の `handleYellowCard` は **今回は変更しない**（AdminDashboard 側は 2-6 の再取得で追従する）。

### 2-6. 画面に戻ったときの自動再取得

既存フック `src/hooks/useVisibilityPolling.ts` を `AdminDashboard.tsx` で使い、
**タブや別アプリから戻ってきたときに users を取り直す**ようにする。

```ts
useVisibilityPolling(
  () => setUsersRefreshKey((k) => k + 1),
  300_000,                 // 5分
  adminTab === 'chat',     // チャット画面を見ているときだけ
  [adminTab],
)
```

- このフックは **表示に戻った瞬間に即実行**する挙動があり、今回の目的（顧客管理タブから戻ったときに反映）にちょうど合う。
- **読み取りコストに注意**：1回の再取得で会員数ぶんの読み取りが発生する。5分間隔で問題ないか、実装役は会員数を踏まえて見積もり、**懸念があれば報告に書くこと**（勝手に間隔を変えてもよいが、変えた理由を必ず報告する）。
- このリポジトリは Firestore の読み取り削減を強く意識している（`chats` をポーリング化した経緯がコメントに残っている）。**onSnapshot への全面移行はしないこと。**

## 1. 仕様のおさらい

- イエローカードは Firestore の `users/{uid}.yellowCards`（数値）で管理
- 付与・取消は2箇所からできる
  - `src/pages/AdminDashboard.tsx` の `handleYellowCard`（チャット画面の顧客詳細）
  - `src/components/UserManager.tsx` の `handleYellowCard`（顧客管理の一覧表）
- 3枚に到達すると `status` が `blacklisted` に変わる
- 顧客リストのアバターは枚数で色が変わる想定
  - 0枚 → 青 `#0095B6` ／ 1枚 → 黄 `#eab308` ／ 2枚以上 → 橙 `#f97316`

---

## 2. こちらで下調べした結果（ここから確認を始めてください）

### 仮説A：アバターの色分けが**1箇所にしか実装されていない**（最有力）

`src/pages/AdminDashboard.tsx` の中に、顧客のアバターを描いている箇所が **4つ** ある。
**色分けが入っているのは1つだけ**で、残り3つは青 `#0095B6` の固定になっている。

| 行 | 場所 | 色分け |
|---|---|---|
| 1157 付近 | 顧客リスト（`sortedUsers.map`） | **あり**（`avatarBg` で分岐） |
| 1109 付近 | 全チャット検索の結果リスト（`globalSearchResults.map`） | **なし**（`bg-[#0095B6]` 固定） |
| 1224 付近 | チャット画面のヘッダー（選択中の顧客） | **なし**（`bg-[#0095B6]` 固定） |
| 1337 付近 | メッセージ左側のアバター（顧客の発言） | **なし**（`bg-[#0095B6]` 固定） |

つまり **チャットを開いて相手とやりとりしている画面のアバターは、何枚カードが付いていても必ず青**。

**確認してほしいこと**

- 上記4箇所の認識が合っているか
- 顧客リスト以外で、色分けが必要なのにされていない箇所が他にもないか（`UserManager.tsx` を含めて全画面を洗う）
- 顧客リストの色分けロジック自体は正しく動くか（0/1/2/3枚で期待どおりの色になるか）

### 仮説B：顧客リストが**リアルタイム更新ではない**

`AdminDashboard.tsx` の users 取得は `onSnapshot` ではなく **`getDocs` の1回取得**で、`usersRefreshKey` が変わったときだけ再取得する作りになっている（150行目付近）。

```ts
const q = query(collection(db, 'users'), where('status', '==', 'active'))
getDocs(q).then(...)
// 依存配列は [usersRefreshKey]
```

`UserManager.tsx` も同様に独自の `usersRefreshKey` を持っており、**2つの画面は状態を共有していない。**

これだと次の場合に色が変わらないはず。

- **別の管理者端末／別のタブ**で付与したとき（開きっぱなしの画面は古いまま）
- **顧客管理（UserManager）で付与して、チャット画面（AdminDashboard）に戻ったとき**（AdminDashboard 側は再取得しない）

オーナーの言う「ちょこちょこ」＝**毎回ではなく特定の操作順のときだけ**、という症状にこれが合致する可能性が高い。

**確認してほしいこと**

- 上記の操作パターンを実際に再現し、どのパターンで色が変わらないかを特定する
- 顧客リスト上部の「更新」ボタンを押す、またはページを再読み込みすると色が変わるか（変わるなら仮説Bが裏付けられる）

### 仮説C：3枚目でブラックリスト入りすると、**リストから消える**

AdminDashboard の users 取得は `where('status', '==', 'active')` で絞っている。
3枚目を付けると `status` が `blacklisted` になるため、**その顧客は顧客リストから消える**はず。

「色が変わらない」ではなく「行ごと消えた」のを、オーナーが色が変わらなかったと受け取っている可能性がある。

**確認してほしいこと**

- 3枚目を付けた直後の挙動（消えるのか、残るのか、再読み込み後どうなるか）
- これが意図した仕様なのか、それとも消えずに橙で残るべきなのか（**判断はせず、現象の報告だけしてください。仕様の決定はオーナーが行います**）

### すでに潰した仮説（再調査不要）

- **Firestore のオフラインキャッシュによる古い値** … `src/lib/firebase.ts` で `memoryLocalCache()` を明示指定しており、ディスクキャッシュは使っていない。ここは原因ではない。
- **`yellowCards` の型ゆれ** … `normalizeYellowCards()` が文字列や `null` も数値に正規化している。ここも原因ではない。

## 3. 追加で見てほしい観点

- `handleYellowCard` の更新が **失敗しても気づけない経路がないか**（`updateDoc` は try/catch で alert が出る作りだが、`setUsersRefreshKey` が呼ばれる前に抜けるパターンがないか）
- `firestore.rules` で `users` の更新が管理者に許可されているか。**権限エラーで書き込みが通っていないケースがないか**（Firestore コンソールで実データの `yellowCards` が実際に増えているかを確認するのが確実）
- 顧客リストの並び替え・絞り込み（`sortedUsers`）の過程で、更新後のデータが反映されない経路がないか
- React の再レンダリングが走らない箇所がないか（`key` の付け方、メモ化など）

## 4. 再現手順（この順で試してください）

1. 管理画面のチャット画面で、ある顧客にイエローカードを1枚付与 → **顧客リストのアバターが黄色になるか**
2. 同じ状態で **チャット画面のヘッダーのアバター**が黄色になるか
3. 同じ状態で **メッセージ左側のアバター**が黄色になるか
4. 全チャット検索を実行し、**検索結果リストのアバター**が黄色になるか
5. 顧客管理（UserManager）で別の顧客に1枚付与 → チャット画面に戻って **色が変わっているか**
6. 5 のあと「更新」ボタンを押す／ページを再読み込みする → **色が変わるか**
7. 2枚目を付与 → 橙になるか
8. 3枚目を付与 → どうなるか（リストから消えるか）
9. 取消（-1）したとき、色が戻るか

各手順で **Firestore コンソールの `users/{uid}.yellowCards` の実値**も併せて確認し、「データは正しいが表示だけ古い」のか「データ自体が更新されていない」のかを切り分けてください。

## 5. 報告してほしいこと

1. **再現条件** … どの画面・どの操作順のときに色が変わらないか。逆に必ず変わるのはどれか
2. **原因** … 仮説A〜Cのどれに当たるか（複数あるなら全部）。仮説外の原因ならその内容
3. **「データは正しいが表示が古い」のか「データが更新されていない」のか** の切り分け結果
4. **修正案** … できれば2案以上。それぞれの
   - 変更するファイルと箇所
   - 影響範囲（他の画面が巻き添えにならないか）
   - リスクと手間の大きさ
   - とくに「色分けを共通化する」案と「その場しのぎで各所に同じ分岐を足す」案の比較
5. **仕様として確認が必要な点**（3枚目でリストから消えるのは正しいのか等）
   → 判断はせず、質問として挙げてください
6. 調査中に見つけた **関連しそうな別の不具合**があれば、それも報告（勝手に直さない）

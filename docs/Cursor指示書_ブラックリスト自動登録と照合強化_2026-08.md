# Cursor指示書｜ブラックリストの自動登録と、再登録防止の強化

対象リポジトリ: `CONV-FKT7-NEW-APP`（VIP Store PWA）
作成日: 2026-08-25
前提: 調査により、**再登録防止機能が事実上まったく機能していない**ことが判明済み

---

## 0. 背景

調査で分かったこと。

| 事実 | 数字 |
|---|---|
| `blacklist` コレクションの件数 | **2件**（テスト用データのみ） |
| `status === 'blacklisted'` の会員 | 141件（うち110件は氏名・メールが空の残骸） |
| 実質的なブラック会員 | **31件** |
| そのうち `blacklist` に登録済み | **1件**（テスト用） |
| **同じ氏名・メールのまま再登録できる人** | **30人** |

**締め出したはずの人が、名前を変えることすらせず再登録できる状態でした。**
実際、8月31日の夜に11分差で2件、停止中アカウントと同一氏名・同一生年月の新規登録が起きています。

### このタスクのゴール（蛇口を締める）

1. **ブラックリストにした瞬間、自動で `blacklist` に登録される**ようにする
2. 登録時の照合を **正規化ありに強化**し、スペースや Gmail のドットでのすり抜けを塞ぐ
3. 既存の実質31件を `blacklist` に**登録し直す**（空の残骸110件は除外）

## 1. ⚠️ このタスクは本番の登録フローを触ります

**`checkBlacklist` が壊れると、誰も新規会員登録できなくなります。**

- 実装 → ローカル確認 → コミット → **オーナーの確認** → デプロイ の順で進めること
- **オーナーの確認なしにデプロイしないこと**
- 第6章の「正常な人が登録できること」のテストを**必ず**行うこと

## 2. 設計（この方針で実装してください）

### 2-1. `blacklist` ドキュメントの形

ドキュメントID = **その会員の uid**（同じ人を二重登録しないため）

```
blacklist/{uid}
{
  uid: string,
  fullName: string,              // 原文（人が見て分かるように）
  email: string,                 // 原文
  normalizedFullName: string,    // 正規化済み
  normalizedEmail: string,       // 正規化済み
  birthMonth: string,            // 照合の精度を上げるため
  memberNumber: number | null,
  reason: string,                // 'auto' | 'backfill' | 'manual'
  createdAt: Timestamp,
  active: boolean,               // true = 有効な登録
  removedAt: Timestamp | null,   // 解除した日時（履歴を残す）
}
```

**既存の2件には `normalizedFullName` などがありません。** 後方互換のため、
照合では**新旧どちらの形でも判定できる**ようにすること（2-3 参照）。

### 2-2. 照合の条件（ここが最重要の設計判断）

**拒否する条件は次の2つだけ。**

| 条件 | 判定 |
|---|---|
| **正規化後のメールアドレスが一致** | **拒否** |
| **正規化後の氏名が一致 かつ 生年月も一致** | **拒否** |
| 正規化後の氏名だけが一致（生年月は違う） | **拒否しない**（ログに残すだけ） |

**氏名だけの一致で拒否してはいけません。**
このアプリの会員にはベトナム系の方が多く、**同姓同名が日本人より格段に多い**ためです。
氏名だけで弾くと、無関係な方が登録できなくなります。

**生年月まで一致すれば別人の確率は大きく下がります。**
8月31日の2件も「氏名＋生年月一致」のパターンなので、この条件で防げます。

### 2-3. 空文字による誤判定を必ず防ぐこと

**`normalizedEmail` や `normalizedFullName` が空文字のドキュメントが `blacklist` にあると、
空のメールで登録しようとした人が全員ヒットする**など、重大な誤判定を招きます。

- **書き込み側**: 氏名またはメールが空の会員は **`blacklist` に登録しない**
- **照合側**: 照合キーが空文字なら、**その条件では照合しない**（スキップする）

この2点は**必ず**入れてください。

### 2-4. 解除への対応

イエローカードを取り消して `active` に戻した会員は、`blacklist` の該当ドキュメントを
**削除せず、`active: false` / `removedAt` を立てる**（論理削除）。

- 照合では `active !== false` のものだけを対象にする
- これにより「過去に一度ブラックだった」履歴が残る
  （現状はカード取消で履歴が完全に消えてしまう。今回の調査で判明した弱点への対処）

> **Firestore の複合インデックスは作らないこと。**
> `normalizedEmail` などの単一条件でクエリし、**`active` の判定は取得後に JavaScript 側で行う**。
> 対象は数十件なので性能上の問題はありません。インデックス追加は運用の手間が増えるため避けます。

## 3. 実装

### 3-1. 正規化ロジックを functions 側にも用意する

**新規ファイル**: `functions/src/normalize.ts`

`scripts/lib/normalize.mjs` と **完全に同じ仕様**で実装すること（TypeScript 版）。

- メール: 小文字化 → `googlemail.com`→`gmail.com` → 対象ドメインのみ `+` 以降除去 → **`gmail.com` のみ**ドット除去
- 氏名: 空白すべて除去 → 全角英数→半角 → ひらがな→カタカナ → 小文字化

> ⚠️ `docomo.ne.jp` / `ezweb.ne.jp` / `au.com` / `softbank.ne.jp` / `i.softbank.jp` / `icloud.com`
> は**ドットを消さない**。ここを間違えると無関係な人を弾きます。

**これで正規化の実装が3箇所目（scripts / functions）になります。**
第6章の同一性テストを必ず通してください。

### 3-2. ブラックリスト入りで自動登録（Cloud Function）

`functions/src/index.ts` の **既存の `onUserUpdated`**（298行目付近）に処理を追加する。

- **既存の会員番号採番の処理は一切変更しないこと。** その後ろに追記する
- 判定: `before.status !== 'blacklisted'` かつ `after.status === 'blacklisted'` になったとき
  → `blacklist/{uid}` に 2-1 の内容で書き込む（`reason: 'auto'`、`active: true`）
- 逆に `before.status === 'blacklisted'` かつ `after.status !== 'blacklisted'` になったとき
  → `blacklist/{uid}` があれば `active: false` / `removedAt` を立てる（**削除しない**）
- **氏名またはメールが空の会員は登録しない**（2-3）。その場合は `console.log` に理由を残す
- 書き込みは冪等にすること（同じ uid で何度呼ばれても1件のまま）
- 例外が起きても**会員番号の採番処理を巻き添えにしないこと**（try/catch で分離）

### 3-3. `checkBlacklist` を正規化照合に変更

`functions/src/index.ts` の `checkBlacklist`（364行目付近）を書き換える。

**現状**（完全一致・OR）

```ts
if (fullName) checks.push(blRef.where('fullName', '==', fullName).limit(1).get())
if (email)    checks.push(blRef.where('email', '==', email).limit(1).get())
```

**変更後の考え方**

1. 受け取った `fullName` / `email` / **`birthMonth`** を**関数側で正規化**する
   （フロントから来る値を信用せず、サーバー側で正規化すること）
2. 正規化メールが空でなければ `where('normalizedEmail', '==', ...)` で取得
3. 正規化氏名が空でなければ `where('normalizedFullName', '==', ...)` で取得
4. **後方互換**: 旧形式の2件のため、`where('email', '==', 生の値)` と
   `where('fullName', '==', 生の値)` の完全一致も併せて実行する
5. 取得した候補から `active === false` のものを除外する
6. 判定
   - メール一致が1件でもあれば → `isBlacklisted: true`
   - 氏名一致のうち、**`birthMonth` も一致するもの**があれば → `isBlacklisted: true`
   - 氏名だけ一致 → **`false`**（ただし `console.log` に記録する）

**`birthMonth` をフロントから送るようにする**

`src/pages/Register.tsx` の `checkBlacklist` 呼び出しに `birthMonth` を追加する。

```ts
const { data } = await fn({
  fullName: name || undefined,
  email: emailAddr || undefined,
  birthMonth: birthMonth || undefined,   // 追加
})
```

- 型定義（`httpsCallable<...>`）も合わせて更新すること
- **呼び出し位置・エラー処理・レート制限は変更しない**
- `birthMonth` が無い呼び出しでも動くこと（`undefined` 許容）

### 3-4. 既存31件のバックフィル（書き込みスクリプト）

**新規スクリプト**: `scripts/backfill-blacklist.mjs`

**これはこのプロジェクトで唯一、Firestore に書き込むスクリプトです。慎重に作ること。**

必須の作り。

- **既定は dry-run**（何も書き込まない）。`--apply` を付けたときだけ実際に書き込む
- dry-run では **対象一覧（会員番号・氏名・メールの伏せ字）と件数**を表示する
- 対象: `status === 'blacklisted'` かつ **氏名とメールの両方が空でない**もの
  → **空の残骸110件は必ず除外**（除外件数も表示すること）
- `role === 'admin'` は除外
- ドキュメントIDは uid。**既に存在する場合は上書きせずスキップ**（件数を表示）
- `reason: 'backfill'`、`active: true`
- 実行後に「登録した件数 / スキップした件数 / 除外した件数」を表示
